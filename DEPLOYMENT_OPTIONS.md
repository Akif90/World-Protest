# Deployment options for World Protest Globe

_Researched against official documentation on 2026-09-12. Provider prices and limits change; recheck the linked pricing pages before creating paid resources. Prices below are USD and exclude domain registration, tax, overages, and optional backups unless stated otherwise._

## What this application actually needs

This is not just a static React site:

- [`frontend/`](frontend/) is a Vite-built React PWA. It can be deployed as static files behind a CDN. Its API address is compiled into the build through `VITE_API_BASE` in [`frontend/src/api.ts`](frontend/src/api.ts).
- [`backend/`](backend/) is a Python 3.12 FastAPI service. It needs a continuously reachable HTTP process and exposes [`/health`](backend/app/main.py).
- PostgreSQL is durable application state. The API creates tables and applies a small set of idempotent DDL statements on startup in [`backend/app/db.py`](backend/app/db.py).
- [`backend/app/ingest/scheduler.py`](backend/app/ingest/scheduler.py) is currently a continuously running process that fetches GDELT data every 15 minutes. On most platforms it is cheaper and safer to make each cycle a short-lived scheduled job that exits.

Low user traffic will keep API and bandwidth usage small, but it does **not** make ingestion or database growth small: the application pulls GDELT every 15 minutes whether anyone visits or not. Database retention, storage alerts, and backups therefore matter from day one.

## Recommendation

Use **Render for the first real deployment**.

It maps cleanly to the current architecture, keeps all four runtime concerns in one place, and offers a useful progression:

1. Deploy a free static frontend, free API, and temporary free Postgres to learn the dashboard and validate configuration.
2. Before the database's 30-day expiry, move to the smallest paid API and paid Postgres and add a 15-minute cron job. The approximate stable floor is $14.30/month, plus actual cron compute, bandwidth/build overages, tax, and the domain.
3. Check in `render.yaml` so the infrastructure definition is versioned with the code.
4. Add GitHub Actions for tests and builds, then change Render auto-deploy from “on commit” to “after CI checks pass.” This is a genuine CI/CD pipeline without requiring deployment credentials in GitHub.

Railway is the closest alternative and may cost less at tiny usage. Choose it instead if keeping the starting bill near $5 is more important than predictable component pricing. Choose the VPS route if the learning goal is specifically Linux/Docker/server administration rather than learning an application platform.

## Application changes and configuration needed before any deployment

1. **Make ingestion one-shot for platform cron.** Export a command that calls `ingest_latest()` and `enrich_batch()` once, then exits. Keep the current blocking scheduler only for local development or a VPS. Running the scheduler inside the web process is unsafe: sleeping services miss runs, and horizontally scaled web instances would ingest in duplicate.
2. **Accept provider database URLs safely.** The app uses SQLAlchemy's explicit `postgresql+psycopg://` driver URL. Many providers expose `postgresql://...`; normalize that scheme on startup or configure the provider variable with `+psycopg`, otherwise SQLAlchemy may look for the uninstalled `psycopg2` driver.
3. **Bind the API publicly.** The production command should bind Uvicorn to `0.0.0.0` and the platform-supplied port, for example `uv run uvicorn app.main:app --host 0.0.0.0 --port $PORT`.
4. **Set the two sides of the browser connection together.** Build the frontend with `VITE_API_BASE=https://api.example.com`, and set backend `ALLOWED_ORIGINS=https://app.example.com` (comma-separated if preview or alternate origins are intentional). These values are documented in [`backend/.env.example`](backend/.env.example).
5. **Use HTTPS from the first public test.** The PWA installation flow requires it, and all recommended managed platforms include it.
6. **Decide data retention before storage fills.** Add a recurring delete/archive policy for old `events` and `event_opens`, monitor database size, and test a restore. GDELT ingestion—not user traffic—sets the baseline growth rate.
7. **Backfill deliberately.** Run the initial backfill as an explicit one-off task against the production database. Do not hide a multi-day backfill inside API startup or every deployment.
8. **Add a real migration tool before schema evolution accelerates.** The current idempotent DDL is acceptable for this first deploy, but the repository already identifies Alembic as the intended next step.

## Suggested learning sequence

### First deployment: manual platform setup

- Create the managed Postgres database.
- Deploy FastAPI and verify `/health` before exposing the frontend.
- Run a small backfill, then query the API.
- Deploy the static frontend with the production API URL.
- Add the one-shot 15-minute ingestion job.
- Attach `app.` and `api.` subdomains, update CORS, and verify HTTPS/PWA installation.
- Exercise one rollback and one database restore while the data is disposable.

### Then add CI/CD

Use one GitHub Actions workflow with separate jobs:

1. Backend: install from `backend/uv.lock`, run `pytest`.
2. Frontend: install with `npm ci`, run `npm test`, lint, and `npm run build`.
3. Deployment: let Render/Railway deploy only after those checks pass. On a VPS or Fly.io, make deployment a third GitHub Actions job using a protected `production` environment and least-privilege secrets.

Keep production deployments serialized with a concurrency group, protect the main branch, and retain a manual `workflow_dispatch` path for controlled redeploys. GitHub Actions supports push/manual triggers, concurrency, environment secrets, branch restrictions, and approval gates in its [deployment documentation](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/control-deployments).

## Options intentionally not recommended for the whole stack

- **GitHub Pages, Cloudflare Pages, Netlify, and Vercel alone** are excellent homes for the compiled frontend, but this application also requires Postgres, a long-lived Python API shape, and 15-minute ingestion. Using one of them alone would require re-architecting the backend and scheduler rather than merely deploying the current application.
- **Kubernetes** adds a control plane, manifests, networking, secrets, persistent volumes, and database operations without solving a current scaling problem. It is a valuable later learning project, not the shortest path to getting this app live.
- **A free Render database as “production”** is a time-limited demo, not durable hosting: it expires after 30 days and has no backups.
